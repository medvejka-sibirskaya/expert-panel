## Ревью пунктов 4.1–4.6

4.1. PID в `run.lock`

Уточнить трактовку

Не стоит считать PID процесса `journal.py` владельцем запуска: он действительно завершается сразу после создания lock.

Для MVP предлагаю:

- координатор передаёт PID долгоживущего процесса Claude Code через `--pid`;
- PID используется как признак того, что запуск, вероятно, ещё активен, а не как абсолютное доказательство;
- живой PID — отказ в новом запуске;
- мёртвый PID — снятие lock только с подтверждением;
- если координатор не может надёжно определить PID, не имитировать надёжность: считать lock эвристическим механизмом защиты от параллельного запуска.

Не нужно строить отдельный механизм мониторинга процессов.

4.2. Перенос повреждённых строк журнала

Для хвостового повреждения текущий подход подходит.

Для повреждения в середине журнала не разрешать автоматическое восстановление: после повреждённой строки могут идти корректные события, автоматическое вмешательство способно нарушить последовательность и целостность истории.

Решение:

- повреждённый хвостовой блок — автоматизированный repair с подтверждением;
- повреждение в середине — остановка и ручной разбор.

4.3. Quarantine в формате JSONL

Принимаю. Важно сохранять исходное содержимое повреждённых строк без потерь, с корректным JSON-экранированием.

4.4. Набор проверок `check_numbers.py`

Оставить как есть. Табличные суммы и денежные форматы — экспертам.

4.5. `compare_reports.py`

Принимаю. Логика кандидатов подходит именно для поиска кандидатов; классификация — за координатором. На пилоте посмотрим ложные совпадения.
