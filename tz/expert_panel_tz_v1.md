# ТЗ: Expert Panel («Экспертная комиссия») — реализация MVP v0.1

**Версия:** 1.0 от 04.11.2026
**Статус:** согласована в диалоге с Медвежкой 04.11.2026; к реализации после сверки §16 по документации Claude Code
**Источники:** спецификация MVP v0.1 (чаты с ChatGPT, файл 5), записка для Жоры от 04.11, аудит hiring-panel (Maxikozie)

## 1. Что строим

Скилл Claude Code **`/expert-panel`** — независимая экспертная комиссия: проверка документов, сборка доказательных замечаний, вердикт, отчёт, журнал запусков.

- **Объекты MVP:** промпты, ТЗ, КП, резюме. **Первый пилот — резюме** (связка с Кадровиком: он готовит → комиссия проверяет → замечания возвращаются ему).
- **Вне MVP:** код, проекты, скиллы, n8n-workflows; SQLite, хеш-цепочки, внешние уведомления, PDF/HTML-экспорт, автоматические исправления, мониторинг (§15 спеки — без изменений).
- **Разделитель ролей:** Библиотекарь (существующий скилл `librarian`, маршрутизация) ≠ Комиссия (`/expert-panel`, глубокое ревью). Комиссия ничего не знает про Библиотекаря и наоборот; связка — отдельная будущая задача.

## 2. Принципы (перечислены в SKILL.md как ограничения поведения)

1. Независимость экспертов: свежий контекст каждому, параллельная волна, заключения друг друга не видят.
2. Каждое замечание — с доказательством (цитатой); без доказательства — не факт, а предположение с пометкой.
3. Скрипты проверяют только форматы и вычислимое (числа, даты, схемы); свободные утверждения сверяет только эксперт-аудитор фактов по цитатам из исходника — скриптовая проверка чисел семантические выдумки не ловит (решение Жоры от 04.11).
4. Комиссия ничего не изменяет в проверяемом материале, не запускает код, не ходит в сеть.
5. Запуск — только после явного разрешения; Preflight ≠ разрешение.
6. Оценки токенов — диапазоном с пометкой «оценка», без денег; оценочное не выдаётся за фактическое.
7. Язык отчётов — русский; имена файлов, технологий, переменных — в оригинале.
8. Гибридный вердикт: комиссия даёт техвердикт; Медвежка может отдельно принять риск — вердикт это не меняет, факт фиксируется в журнале и отчёте.

    ├── expert-style.md           # редактор (стиль, ясность)
    └── expert-judge.md           # судья

D:\expert-panel\                 # ДАННЫЕ (отдельно от проверяемых проектов)
├── history\history.jsonl         # журнал событий, append-only

Префикс `expert-` — чтобы не пересекаться с агентами Медвежки (`barrymore`, `kadrovik`…) и чтобы файлы комиссии стояли в списке одним блоком. Имена файлов агентов — латиница в нижнем регистре (техническое требование Claude Code); названия ролей и весь текст внутри — русские.

Определения агентов дают две гарантии: набор инструментов `Read, Glob, Grep` (редактировать нечем) и закреплённую модель за ролью.

## 4. Роли и модели (смешанное распределение — решение Медвежки от 04.11)

| Роль | Модель по умолчанию | Что делает |
|---|---|---|
| expert-facts (аудитор фактов) | полная | сверяет утверждения документа с исходником по цитатам; ловит выдумки |
| expert-domain (предметник) | полная | экспертиза по типу документа (для пилота — HR/резюме) |
| expert-critic (критик) | флэш | adversarial-взгляд: слабые места, пробелы, риски |
| expert-style (редактор) | флэш | типовые проверки: структура, ясность, формат, консистентность |
| expert-judge (судья) | **только полная** | сводит, проверяет доказательства, вердикт |

Численность (ориентиры, уточняются практикой): простая проверка — 2–3 эксперта, стандартная — 3–4, глубокая — 5–7. Координатор может поменять модель конкретному эксперту с обоснованием в Preflight — согласуется отдельной строкой.

**Состав пилота (резюме, стандартная глубина):** expert-facts + expert-domain (HR) + expert-critic + expert-style — 4 эксперта, судья expert-judge.

## 5. Сценарий запуска (ядро SKILL.md)

1. **Вход:** `/expert-panel` + материалы (файлы/пути; по умолчанию — из диалога или от Кадровика). КЛОДИ-главная принимает роль координатора.
2. **Изучение:** координатор читает материалы (только Read/Glob/Grep), определяет тип объекта, объём, релевантные части; нерелевантное (кэш, бинарники, зависимости) исключает и показывает в границах.
3. **Секреты — до экспертов:** `scan_secrets.py` по материалам; находки → раздел Preflight (файл/строка/тип, значение не показывается).
4. **Preflight** (раздел 6) → показывается в чате.
5. **Явное разрешение.** Молчание/«посмотрим» ≠ разрешение.
6. **Волна экспертов:** все субагенты запускаются **одним сообщением** (параллельно, свежий контекст каждому). Бриф эксперта = роль + пути материалов + формат замечаний. Про чужие заключения в брифе ни слова.
7. **Стык-контроль:** координатор сравнивает фактический расход (оценка по объёму брифов/ответов) с согласованным Preflight. В пределах — дальше; превышение резерва — стоп и вопрос Медвежке. Механической остановки внутри фазы нет — контроль только на стыках.
8. **Судья:** expert-judge получает все заключения + пути исходников (может перечитать сам), объединяет дубли, проверяет доказательства, классифицирует, выносит вердикт.
9. **Отчёт + журнал:** `report.py` рендерит MD и JSON с общим UUID; `journal.py` дописывает события; координатор показывает резюме и пути файлов.

## 6. Preflight — обязательный состав

1. Цель проверки и тип задачи
2. Изученные материалы (пути + объём) и исключённое (кэш, нерелевантное, нечитаемое)
3. Глубина: целевая / связанная / комплексная — и границы проверки
4. Состав экспертов, роли, модели (включая отклонения от профиля — с обоснованием)
5. Предполагаемое количество вызовов (эксперты + судья + резерв)
6. **Оценка токенов диапазоном** (input/output раздельно, пометка «оценка», без денег)
7. Ограничения и неопределённости (что проверить не сможем)
8. Критерии приёмки
9. Место сохранения отчётов (по умолчанию `D:\expert-panel\reports\`; в папку проверяемого проекта — только в отдельную подпапку, утверждённую здесь же)
10. Режим конфиденциальности + находки `scan_secrets` (если есть) и предлагаемый способ обработки
11. Предложение сравнения с предыдущей проверкой (если объект уже проверялся)

**После утверждения Preflight** координатор не может сам: добавить экспертов, сменить модели, добавить этапы, расширить резерв вызовов. Любое изменение — новое согласование. Recheck — всегда новый запуск с новым Preflight.

## 7. Замечание — единая схема (для JSON-отчёта)

| Поле | Значение |
|---|---|
| id | уникальный в рамках проверки (F-1, F-2… или UUID) |
| priority | Критично / Важно / Желательно / Вопрос |
| type | подтверждённая / вероятная / предположение / субъективная |
| location | файл, строка или раздел документа |
| evidence | цитата из исходника (обрезана, секрет-маска применена) |
| problem | что не так |
| consequence | что из этого следует |
| recommendation | как исправить |
| confidence | степень уверенности автора |

Правило классификации: доказательств недостаточно → тип не «подтверждённая», без исключений. «Подтверждённая» может опираться на: цитату исходника (факт-аудитор), вычислимую проверку скрипта (числа/даты/схемы) — и ни на что больше.

## 8. Оценка и вердикт

- Шкала по критериям (адаптируется под тип документа): 0 — не выполнено, 1 — существенные недостатки, 2 — частично, 3 — хорошо, 4 — полностью и подтверждено; N/A; «Не проверено». Непроверенный критерий не даёт полной оценки без оговорки.
- Вердикт: **Принято / Принято с замечаниями / Не принято.** Критичная проблема или невыполнение обязательного требования блокирует «Принято». Итог не выводится из среднего балла.
- Гибрид: Медвежка принимает риск — в отчёте раздел «Принятые пользователем риски», техвердикт неизменен, событие в журнале.

## 9. Отчёты

Два файла на запуск, общий UUID: `<UUID>.md` (человекочитаемый) и `<UUID>.json` (структурированный).

Разделы MD: общий вердикт → краткое обоснование → оценка по критериям → критичные → важные → желательные → вопросы → разногласия экспертов (судья сохраняет обоснованные, не глушит) → проверенные области → непроверенные области → ограничения → рекомендации и порядок исправлений → статистика токенов (с пометкой «оценка») → принятые пользователем риски.

## 10. Журнал JSONL

`D:\expert-panel\history\history.jsonl`, append-only, каждая строка-событие: `uuid, seq, utc_ts, schema_version, event_type, data`.

Типы событий MVP: `run_started, preflight_shown, preflight_approved, secret_finding (значение маскировано), phase_experts_started, expert_finished (роль, модель, оценка токенов), checkpoint_passed, judge_finished, report_saved (пути), risk_accepted_by_user, run_finished, run_stopped (причина), report_deleted`.

- **Целостность без хеш-цепочки** (отложена, решение Медвежки 04.11): `journal.py check` — каждая строка парсится как JSON, `seq` непрерывен, `uuid` уникальны, `schema_version` поддерживается.
- **Удаление (согласованная политика):** Медвежка может удалить файлы отчёта; в журнал пишется `report_deleted` (id, когда; содержимое отчёта в событие не попадает). Прежние события журнала не переписываются никогда. Полная физическая очистка истории — не MVP.

## 11. Секреты

1. `scan_secrets.py` (регэкспы: Bearer/token=/api_key=/password=, Telegram-токен, вебхуки) гоняется **до** Preflight — это эвристика, гарантии покрытия нет, честно отражается в Preflight и отчёте.
2. Находка показывается как «файл, строка, тип» — без значения.
3. Варианты продолжения (выбирает Медвежка в Preflight): **(а)** маскированная копия участка — эксперты работают с ней (маску делает скрипт), **(б)** участок исключается из проверки, фиксируется как непроверенный, **(в)** остановка запуска. По умолчанию — (а).
4. Значение секрета не попадает: в диалог, в брифы экспертов, в заключения, в отчёты, в журнал. Судья и `report.py` дополнительно прогоняют маску регэкспов по финальным текстам.

## 12. Recheck и сравнение

- Recheck = новый запуск, новый Preflight, новое разрешение. Координатор изучает исправленные участки, определяет связанные части, предлагает объём повтора.
- Сравнение с прошлым отчётом (`compare_reports.py`): новые / устранённые / повторившиеся / изменившиеся замечания. Сравнение не подменяет новый вердикт.

## 13. Скрипты Python (технические операции, решений не принимают)

| Скрипт | Что делает |
|---|---|
| `extract_text.py` | md/txt/код — как есть; docx/xlsx — через python-docx/openpyxl; pdf — нативно Read. Нечитаемое — отчёт «не читается», не молча |
| `scan_secrets.py` | эвристический поиск секретов, вывод файл/строка/тип, значение маскируется |
| `check_numbers.py` | вычислимое: числа, даты, суммы, схемы — внутренняя непротиворечивость документа |
| `journal.py` | append / list / read / check событий JSONL |
| `report.py` | сборка MD+JSON из данных вердикта, валидация схемы отчёта |
| `compare_reports.py` | сравнение двух отчётов по категориям §12 |

Общее правило: ни один скрипт не пишет в проверяемые материалы и не принимает решений за пользователя.

## 15. Приёмка MVP

Комиссия готова к пилоту, когда за один полный прогон: приняты материалы → изучены → Preflight показан → разрешение получено → эксперты отработали независимо → судья свёл → вердикт обоснован → MD+JSON созданы и валидны → события в журнале, `journal.py check` проходит → исходные материалы не изменены (проверяется `git status`/сравнением хешей).

**Пилот:** 3 реальных резюме от Кадровика. Успех = Медвежка признаёт замечания полезными (доказательные, без выдумок), а не формально пройденный чек-лист.
