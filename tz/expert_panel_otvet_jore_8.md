# Expert Panel — ответ Жоры №8 (v1.5: автономный агент)

В целом согласен с направлением v1.5. Это правильное развитие Expert Panel: автономность, адаптивность и скорость без потери надёжности.

Но я бы внёс три небольших уточнения до синхронизации ТЗ.

## 1. Автономный прогон — согласовано

Полностью поддерживаю.

После утверждения Preflight координатор самостоятельно выполняет весь сценарий:

- определяет тип документа;
- формирует комиссию;
- готовит задания;
- запускает экспертов;
- собирает заключения;
- запускает судью;
- при включённой редактуре запускает редактора;
- формирует и сохраняет результаты.

Никаких промежуточных подтверждений.

Единственная точка согласования — Preflight. Утверждённые границы нельзя менять самостоятельно.

## 2. Адаптивная комиссия — согласовано с уточнением

Таблица разумная. Не нужно запускать четыре экспертные роли для каждого типа документа.

| Документ | Обязательные | Опциональные |
| --- | --- | --- |
| Резюме | facts, domain (HR), critic, style | — |
| Промпт | facts, critic | style |
| ТЗ | domain, facts, critic | style |
| КП | domain, facts, critic | style |

Почему facts обязателен для КП: коммерческое предложение содержит цены, сроки, обязательства и характеристики. Ошибки в этих сведениях могут иметь практические последствия.

Ещё одно условие: предметный эксперт должен соответствовать области документа. Нельзя назначать HR-эксперта для проверки технического ТЗ только потому, что у нас есть такая роль.

## 3. Компактные брифы — согласовано с уточнением

Это действительно может ускорить работу.

Но важно различать объём передаваемого текста и объём полномочий эксперта.

- Facts по-прежнему видит весь документ.
- Critic должен видеть достаточно контекста, чтобы находить противоречия между разделами.
- Domain получает материал, необходимый для предметной оценки.
- Style получает текст целиком или достаточный контекст для оценки последовательности и единообразия.

Главное: каждый эксперт работает в своей области, но не теряет необходимый контекст.

Не нужно искусственно сокращать брифы до минимума, если это ухудшает качество.

## 4. Чистый edited — согласовано

Служебные маркеры `[абзац N]` в итоговом документе не нужны.

Оставляем:

- исходную структуру документа;
- заголовки и нумерацию;
- таблицы;
- маски контактов `[ТЕЛЕФОН]`, `[EMAIL]`;
- естественный читаемый текст.

Служебные маркеры остаются в рабочих копиях и используются для доказательств и привязки замечаний.

## 5. Итоговое решение

- Автономный прогон — да.
- Адаптивная комиссия — да.
- Компактные брифы — да.
- Чистый edited — да.
- Новая инфраструктура — не нужна.

Мой вердикт: v1.5 можно синхронизировать с ТЗ с учётом этих уточнений.

И ещё один важный момент относительно скорости: адаптивная комиссия уменьшит количество вызовов моделей для некоторых документов, но сама по себе не гарантирует завершение проверки за пару минут. Нужно будет измерить время реальных запусков после внедрения.

Не надо сейчас создавать дополнительные оптимизационные подсистемы. Реализуем v1.5, проверим на документах и посмотрим на фактическую скорость.
