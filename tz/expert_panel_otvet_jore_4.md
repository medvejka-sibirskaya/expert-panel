# Ответ Жоры №4 — ревью этапа 0.3 (записка №4), 05.11.2026

Этап 0.3 считаю успешно пройденным, но с одним блокирующим замечанием перед пилотом: сейчас система не гарантирует правильную привязку O-имени к физическому файлу. Это не косметическая ошибка отчёта. Она разрушает доказательную основу комиссии: цитата может быть настоящей, но приписанной не тому документу.

Находка существенная. Особенно показательно, что судья подтвердил все 26 цитат, потому что проверял их по той же ошибочной карте. Значит, предусмотренная независимая проверка судьёй здесь действительно не сработала.

Ниже — решения по пунктам.

## 4.1. Механическая сверка доказательств

Согласен. До пилота

Добавить отдельный `verify_evidence.py`, а не расширять `check_numbers.py`.

Это разные задачи:

- `check_numbers.py` проверяет вычислимые факты: даты, суммы, нумерацию.
- `verify_evidence.py` проверяет связь замечания с исходным доказательством.

Минимальный функционал:

1. Получает замечания экспертов и разрешённые копии документов.
2. Для каждого замечания извлекает O-имя и цитату.
3. Проверяет, находится ли нормализованная цитата в указанном физическом O-файле.
4. При несовпадении возвращает отдельный результат для координатора.
5. Ничего не исправляет автоматически и не меняет исходное заключение эксперта.

Предлагаю три результата проверки:

| Статус         | Значение                                      |
| -------------- | --------------------------------------------- |
| `verified`     | Цитата найдена в указанном файле              |
| `mismatch`     | Цитата не найдена в указанном файле           |
| `unverifiable` | Цитату нельзя надёжно проверить автоматически |

Нормализация должна быть ограниченной: пробелы, переносы строк, типографские различия. Не нужно превращать проверку в семантический поиск, который будет считать похожие фразы совпадением.

Важное ограничение: проверка цитаты сама по себе не устанавливает правильность карты O1 → физический файл. Если координатор ошибочно назвал файлы, проверка должна работать по заранее созданному манифесту соответствий, а не по повторному листингу папки.

Результат `mismatch` должен поступать координатору и судье как предупреждение о ненадёжном доказательстве. Судья не должен подтверждать такое замечание как проверенное.

## 4.2. Контрольный якорь в брифе

Согласен. Внести в SKILL.md

Но я бы сделал якорь частью более надёжного решения.

Не просить эксперта самостоятельно определять O-имена по порядку файлов. Координатор заранее создаёт однозначный манифест:

```
O1.md → физический файл разрешённой копии №1
O2.md → физический файл разрешённой копии №2
```

Дальше каждый эксперт получает:

- точный путь к каждому файлу;
- его O-имя;
- короткий контрольный якорь из начала документа.

Например:

```
O1.md
Путь: <точный путь к копии>
Контрольный якорь: первый раздел [Опыт], период 2019–2022.

O2.md
Путь: <точный путь к копии>
Контрольный якорь: первый раздел [Навыки].
```

Якорь — дополнительная страховка, а не основной механизм идентификации.

Ещё одно небольшое правило: эксперты читают только перечисленные в брифе файлы. Не используют `Glob` для самостоятельного определения порядка документов. Если нужно открыть файл, используют указанный путь.

Это простое изменение, не требующее новой архитектуры.

## 4.3. Проверка суммы периодов стажа

Согласен с включением в пилотный пресет

Не стал бы добавлять этот класс в общий набор `check_numbers.py` безусловно.

Причина: расчёт стажа не всегда равен простой сумме периодов. Возможны:

- пересекающиеся периоды работы;
- одновременная работа в нескольких организациях;
- неполные месяцы;
- периоды, указанные только годами;
- округление общего стажа.

Для пилота резюме предлагаю добавить отдельную проверку в пресет типа `resume`.

Её задача — выявлять арифметическое противоречие между заявленным стажем и датами работы, но не самостоятельно устанавливать окончательный стаж.

Правило для первой версии:

- учитываются явно указанные периоды;
- пересекающиеся периоды не суммируются дважды;
- неполные и неоднозначные даты не превращаются в точные значения без согласованного правила;
- результат — вычислимое расхождение для экспертов и судьи, а не автоматический вывод о недостоверности резюме.

Важный момент: если точные правила подсчёта месяцев и округления пока не определены, лучше выдавать предупреждение, а не категоричный вердикт.

## 4.4. Исправление `report.py`

Согласен. Исправить до пилота

Замечание подтверждено описанным воспроизведением: некорректный `preflight_summary` проходит валидацию, после чего рендеринг MD падает, оставляя JSON без MD.

Минимальный фикс:

1. В `_validate` проверить, что `preflight_summary` — объект ожидаемой структуры.
2. При неверном типе вернуть `invalid_schema`.
3. Добавить тест: строка вместо объекта → `invalid_schema`, ни одного файла отчёта не создано.

Есть ещё одно полезное уточнение: оба формата отчёта желательно сначала сформировать в памяти и только после успешного рендеринга начинать запись. Это предотвращает частичную запись при ошибке формирования второго формата.

Не нужно ради этого переписывать механизм отчётности целиком.

## 4.6. Разнообразие семейств моделей

Рекомендация, не требование MVP

Согласен, что одинаковое семейство моделей может иметь общие слепые зоны. Но обязательное распределение ролей между разными семействами сейчас вводить не нужно.

Почему:

- наличие другого семейства не гарантирует независимость ошибок;
- доступность моделей и шлюзов может меняться;
- обязательное распределение усложнит Preflight;
- текущий MVP не должен зависеть от наличия конкретных поставщиков моделей.

Предлагаю записать в рекомендации для координатора:

> При наличии доступных моделей разных семейств можно рассмотреть распределение хотя бы одной экспертной роли на другое семейство. Это дополнительная мера снижения риска коррелированных ошибок, а не обязательное условие запуска комиссии.

В Preflight можно учитывать этот фактор при выборе моделей, но не блокировать запуск из-за отсутствия альтернативного семейства.
