# ТЗ: Expert Panel («Экспертная комиссия») — реализация MVP v0.1

**Версия:** 1.5 от 05.11.2026 (заменяет v1.4)
**Статус:** автономный агент — автономный прогон после Preflight, адаптивная комиссия, компактные брифы, чистый `edited` без маркеров (согласовано с Жорой — ответ №8, и Медвежкой). Правки внесены в SKILL.md; v1.5 фиксирует их в ТЗ
**Источники:** спецификация MVP v0.1 (чаты с ChatGPT), ревью ТЗ v1.0 / v1.1 / v1.2 / v1.4 / v1.5 (Жора), согласования правок, аудит hiring-panel (Maxikozie)

## 1. Что строим

Скилл Claude Code **`/expert-panel`** — независимая экспертная комиссия: проверка документов, сборка доказательных замечаний, вердикт, отчёт, журнал запусков.

- **Объекты MVP:** промпты, ТЗ, КП, резюме. **Первый пилот — резюме** (связка с Кадровиком: он готовит → комиссия проверяет → замечания возвращаются ему).
- **Вне MVP:** код, проекты, скиллы, n8n-workflows; SQLite, хеш-цепочки, внешние уведомления, PDF/HTML-экспорт, автоматические исправления исходника, запись DOCX, восстановление реальных контактов, обратимая маска, мониторинг, OCR (§15 спеки — без изменений).
- **Форматы чтения** (что система технически умеет обрабатывать): md, txt, docx, pdf, xlsx. Код и ipynb в MVP исключены полностью.
- **Редактура (в MVP с v1.4):** опциональный этап после судьи — если редактура включена в Preflight, корректор **автоматически** исправляет все подтверждённые замечания и комиссия выдаёт **два результата**: исправленную маскированную Markdown-копию `edited_O*.md` и отдельный файл пояснений `changes_O*.md` (§5, шаг 11a). Редактура не изменяет исходник и не меняет вердикт исходной проверки. Полный цикл (запись DOCX, реальные контакты, сохранение форматирования) — вне MVP, отдельным этапом.
- **Автономность (v1.5):** после утверждения Preflight координатор ведёт весь сценарий сам (определяет тип → состав → брифы → волна → судья → редактура → отчёт) без промежуточных подтверждений; Preflight — единственная точка согласования; утверждённые границы менять нельзя.
- **Разделитель ролей:** Библиотекарь (существующий скилл `librarian`, маршрутизация) ≠ Комиссия (`/expert-panel`, глубокое ревью). Комиссия ничего не знает про Библиотекаря и наоборот; связка — отдельная будущая задача.

## 2. Принципы (перечислены в SKILL.md как ограничения поведения)

1. Независимость экспертов: свежий контекст каждому, параллельная волна, заключения друг друга не видят.
2. Каждое замечание — с доказательством (цитатой); без доказательства — не факт, а предположение с пометкой.
3. Скрипты проверяют только форматы и вычислимое (числа, даты, схемы); свободные утверждения сверяет только эксперт-аудитор фактов по цитатам из исходника — скриптовая проверка чисел семантические выдумки не ловит.
4. Комиссия не изменяет исходный материал, не запускает код, не ходит в сеть. Агенты не видят исходных файлов — только разрешённые текстовые копии. Опционально комиссия создаёт исправленную маскированную Markdown-копию (редактура, §5 шаг 11a) — исходник при этом не изменяется.
5. Запуск — только после явного разрешения; Preflight ≠ разрешение.
6. Оценки токенов — диапазоном с пометкой «оценка», без денег; оценочное не выдаётся за фактическое.
7. Язык отчётов — русский; имена файлов, технологий, переменных — в оригинале (за исключением исходных имён материалов с ПД — см. §11).
8. Гибридный вердикт: комиссия даёт техвердикт; Медвежка может отдельно принять риск — вердикт это не меняет, факт фиксируется в журнале и отчёте.
9. Один активный запуск в момент времени — инструкцией и механизмом lock-файла (§10).
10. Значения потенциальных секретов не выводятся сканером ни в stdout, ни в stderr, ни в диагностические логи; то же — для контактных ПД (§11).
11. Немаскированный текст материалов живёт только в памяти скриптов; на диск пишутся только маскированные разрешённые копии (§11).

## 4. Роли и модели

Точные идентификаторы (подтверждены Медвежкой 04.11): **полная** = `glm-5.3:cloud`, **флэш** = `glm-5.3-flash:cloud` (точное написание дополнительно сверить по шлюзу при реализации, §14). Модель — параметр frontmatter роли: замена модели (в т.ч. будущие DeepSeek/Kimi) архитектуру не меняет.

| Роль | Модель по умолчанию | Что делает |
|---|---|---|
| expert-facts (аудитор фактов) | полная | сверяет утверждения документа с исходником по цитатам; ловит выдумки |
| expert-domain (предметник) | полная | экспертиза по типу документа (для пилота — HR/резюме) |
| expert-critic (критик) | флэш | adversarial-взгляд: слабые места, пробелы, риски |
| expert-style (редактор) | флэш | типовые проверки: структура, ясность, формат, консистентность |
| expert-editor (корректор) | **полная** | исполнитель: применяет к маскированной копии все подтверждённые замечания; не участвует в волне, запускается после судьи |
| expert-judge (судья) | **только полная** | сводит, проверяет доказательства, вердикт |

Разделение ролей `expert-style` и `expert-editor`: редактор **оценивает** материал (находит проблемы стиля, структуры, подачи), корректор **применяет** согласованные исправления после суда. Это разные задачи — объединять их нельзя: иначе один агент одновременно оценивал бы собственные исправления и решал бы, что менять. `expert-editor` — исполнитель редакторских решений, а не дополнительный эксперт.

Численность (ориентиры, уточняются практикой): простая проверка — 2–3 эксперта, стандартная — 3–4, глубокая — 5–7. Координатор может поменять модель конкретному эксперту с обоснованием в Preflight — согласуется отдельной строкой. Смешение моделей внутри одного прогона — только по явному решению Медвежки в Preflight.

**Адаптивная комиссия (v1.5):** состав подбирается под тип документа, чтобы не гонять роли без нужды:

| Тип документа | Обязательные роли | Опциональные роли |
|---|---|---|
| Резюме (пилот) | facts + domain (HR) + critic + style | — |
| Промпт | facts + critic | style |
| ТЗ | domain (предметник области) + facts + critic | style |
| КП (коммерческое) | domain (предметник) + facts + critic | style |

Судья expert-judge — всегда; корректор expert-editor — только при включённой редактуре. Роль domain всегда соответствует области документа (для технического ТЗ — предметник области, а не HR-эксперт); предметная роль назначается по типу/теме документа, а не «из тех, что есть». Итоговый состав фиксируется в Preflight п.4 (координатор предлагает по таблице, отклонения — с обоснованием); после утверждения менять его без нового согласования нельзя. **Состав пилота (резюме, стандартная глубина):** expert-facts + expert-domain (HR) + expert-critic + expert-style — 4 эксперта (полный состав, отработан на пилоте). Редактор исключается при целевой проверке фактов — по решению в Preflight. **При включённой редактуре** дополнительно запускается expert-editor (корректор) — после судьи, автоматически по всем подтверждённым замечаниям; в первоначальной волне он не участвует. При выключенной редактуре корректор не запускается и его вызов не оплачивается.

## 5. Сценарий запуска (ядро SKILL.md)

0. **Блокировка и остатки:** `journal.py lock` создаёт `run.lock` (PID + run_id). Живой чужой lock → отказ. Lock от мёртвого процесса (аварийное завершение предыдущего запуска) → снятие по подтверждению Медвежки. Обнаружены рабочие папки `work\` от незавершённых запусков → предложение удалить — удаление только по подтверждению, автоматически никогда.
1. **Вход:** `/expert-panel` + материалы (файлы/пути; по умолчанию — из диалога или от Кадровика). КЛОДИ-главная принимает роль координатора.
2. **Инвентаризация без чтения:** метаданные (имя, размер, формат). Лимиты: файл ≤ 5 МБ, ≤ 20 файлов; сверх — согласование в Preflight (допущение). Материалы получают **обезличенные отображаемые имена** O1, O2… — используются везде дальше (Preflight, журнал, отчёты, заключения); исходные пути с потенциальными ПД в них не попадают (§11).
3. **Извлечение текста — только в память скрипта, на диск не пишется:** `extract_text.py`: md/txt — как есть; docx — python-docx; xlsx — openpyxl; pdf — текстовый слой. В текст вставляются **маркеры привязки**: страница (pdf) / лист+строка (xlsx) / абзац (docx) / строка (md, txt). Статусы извлечения: «извлечено» либо «не извлекается» (повреждён, зашифрован, **pdf-скан без текстового слоя, пустой результат**) — последнее означает «не проверено на секреты» и честно отражается в Preflight и отчёте. Промежуточный (немаскированный) текст — только в памяти; временные открытые файлы запрещены.
4. **Сканирование текста в памяти** (`scan_secrets.py`): два набора паттернов — секреты (Bearer/token=/api_key=/password=, Telegram-токен, вебхуки) и **контактные ПД** (телефоны РФ, email, адреса). Вывод — только O-имя, маркер привязки, тип; значения не выводятся ни в диалог, ни в stdout/stderr, ни в логи. Ничего не маскируется и не копируется до выбора режима.
5. **Preflight** (раздел 6): план, границы, эксперты, оценка токенов, находки сканера, режим обработки секретов (предложение по умолчанию — маскирование), место и срок хранения.
6. **Явное разрешение.** Молчание/«посмотрим» ≠ разрешение. Утверждение Preflight — **единственная точка согласования**: дальше (шаги 7–13) координатор выполняет утверждённый сценарий автономно, промежуточные подтверждения не требуются.
7. **Формирование разрешённых копий — после выбора режима:** текст извлекается повторно (в памяти), обрабатывается и только затем пишется в `work\<run_id>\`. Режимы относятся **только к секретам**: (а) маскирование; (б) исключение участков (исключённое фиксируется как непроверенное); (в) остановка запуска. **Контактные ПД маскируются в каждой разрешённой копии в любом режиме, без исключений.** Маркеры привязки сохраняются. Разрешённая копия — первый и единственный дисковый артефакт запуска до отчёта.
8. **Чтение координатором — только разрешённых копий:** тип объекта, объём, границы; нерелевантное исключается и показывается в Preflight-границах (до разрешения — только перечень, без содержимого).
9. **Волна экспертов:** все субагенты запускаются **одним сообщением** (параллельно, свежий контекст каждому). Бриф эксперта компактный: роль + зона ответственности (что проверяет именно этот эксперт) + пути разрешённых копий в `work\<run_id>\` + формат замечаний. «Компактность» — про чёткую зону ответственности, а не про искусственное урезание материала: facts видит весь документ, critic — достаточно контекста для противоречий между разделами, domain — нужный для предметной оценки материал, style — текст целиком или достаточный контекст. Про чужие заключения в брифе ни слова.
10. **Стык-контроль:** координатор сравнивает фактический расход (оценка по объёму брифов/ответов) с согласованным Preflight. В пределах — дальше; превышение резерва — стоп и вопрос Медвежке. Механической остановки внутри фазы нет.
11. **Судья:** expert-judge получает все заключения + те же разрешённые копии, объединяет дубли, проверяет доказательства, классифицирует, выносит вердикт.
11a. **Редактура (опционально, только если заявлена в Preflight):** после суда корректор `expert-editor` (read-only, полная модель) получает на вход маскированную копию + полное заключение комиссии и **автоматически исправляет все подтверждённые замечания** (тип «подтверждённая»); замечания «вероятная», «предположение», «субъективная» не исправляются. Отдельное подтверждение каждого замечания и выбор ID Медвежкой не требуются. Корректор возвращает полный исправленный текст + пояснения (id → что изменено → почему). Правила правки — §5а. Координатор **пост-маскирует** результат и записывает два файла в `reports\<run_id>\`: `edited_O*.md` (исправленная копия — готовый к использованию текст **без служебных маркеров привязки `[абзац N]`**; исходная структура, заголовки, нумерация, таблицы и маски контактов `[ТЕЛЕФОН]`/`[EMAIL]` сохраняются) и `changes_O*.md` (пояснения: что исправлено, почему, основание — какое замечание, какие подтверждённые не удалось исправить и почему). Перед сохранением координатор сверяет diff с исходной маскированной копией: изменения соответствуют подтверждённым замечаниям, новых фактов и незаявленных содержательных изменений нет, маски контактов сохранены, исходник и разрешённая копия не изменены. Нарушение границ → результат не публикуется, координатор сообщает о проблеме. Редактура не меняет вердикт исходной проверки.
12. **Отчёт + журнал:** `report.py` рендерит MD и JSON с общим run_id (при редактуре — со ссылками на `edited_O*.md` и `changes_O*.md` и статусом `editor_stage`); прогоняет **пост-маску** (секреты + контактные ПД) по всем финальным текстам — эксперт мог воспроизвести контакт в замечании, маска обязана его поймать; валидация схемы. Координатор проверяет просроченные отчёты (retention) и предлагает удалить — только по подтверждению.
13. **Завершение — два разных случая:**
    - **Штатная остановка или перехваченная ошибка** (координатор жив): lock снимается сам; остатки `work\<run_id>\` — вопрос Медвежке немедленно: удалить (по подтверждению) или сохранить (по явной просьбе).
    - **Аварийное завершение** (Claude Code упал, питание снято — код не выполняется): lock **остаётся** на диске; снять его в этот момент физически невозможно. Следующий запуск обнаруживает lock мёртвого процесса → снятие по подтверждению (шаг 0); остатки `work\` → предложение удалить по подтверждению.

## 5а. Редактура — правила правки (обязательные для корректора)

**Что считается «принятым замечанием»:** корректор исправляет только замечания с типом «подтверждённая». Замечания типов «вероятная», «предположение», «субъективная» не исправляются автоматически — при необходимости они лишь упоминаются в `changes_O*.md` как оставленные без изменения. Если для устранения подтверждённого замечания недостаточно сведений — оно остаётся без исправления с объяснением причины.

Четыре правила правки:

1. **Основание.** Каждое содержательное изменение связано с ID замечания, подтверждённого судьёй.
2. **Минимальность.** Изменяется только фрагмент, необходимый для устранения замечания; допускаются локальные грамматические и синтаксические правки для связности.
3. **Запрет новых фактов.** Корректор не придумывает достижения, обязанности, навыки, результаты, даты и количественные показатели.
4. **Сохранение неопределённости.** Если замечание требует сведений, которых нет в исходнике, корректор не додумывает их, а оставляет фрагмент без изменения (пример: «увеличение выручки на 30%» без указания периода — период неизвестен, «за год» вписывать нельзя).

**Редактура не меняет вердикт:** вердикт относится к проверенному исходному материалу. Успешная редактура не означает, что исходный документ получил новый вердикт «Принято». Проверка исправленной версии — отдельный запуск Expert Panel (Recheck, §12).

## 6. Preflight — обязательный состав

1. Цель проверки и тип задачи
2. Материалы под O-именами (формат, объём) и исключённое; нечитаемое/зашифрованное/pdf-без-текстового-слоя — отдельной строкой со статусом «не проверено на секреты»; отклонения от лимитов — с обоснованием
3. Глубина: целевая / связанная / комплексная — и границы проверки
4. Состав экспертов, роли, модели — по адаптивной таблице (§4): обязательные роли по типу документа, опциональные — по глубине; отклонения от таблицы — с обоснованием
5. Предполагаемое количество вызовов (эксперты + судья + резерв)
6. **Оценка токенов диапазоном** (input/output раздельно, пометка «оценка», без денег)
7. Ограничения и неопределённости (что проверить не сможем)
8. Критерии приёмки (для пилота — базовый набор §15)
9. Место сохранения отчётов (по умолчанию `D:\expert-panel\reports\`; в папку проверяемого проекта — только в отдельную подпапку, утверждённую здесь же) и срок хранения (retention_days, §11)
10. **Находки сканера** (O-имя, маркер привязки, тип — без значений) и **предлагаемый режим обработки секретов** (по умолчанию — маскирование); выбор режима — часть утверждения Preflight. Контактные ПД маскируются всегда — не предмет выбора.
11. Предложение сравнения с предыдущей проверкой (если объект уже проверялся)
12. **Редактура:** нужна ли (да/нет); если да — состав корректора (expert-editor, полная модель) и место выдачи (`reports\<run_id>\edited_O*.md` + `changes_O*.md`). Включение редактуры в Preflight означает автоматическое исправление всех подтверждённых замечаний — отдельный выбор ID Медвежкой не требуется.

**После утверждения Preflight** координатор не может сам: добавить экспертов, сменить модели, добавить этапы, расширить резерв вызовов, сменить режим обработки. Любое изменение — новое согласование. Recheck — всегда новый запуск с новым Preflight.

## 7. Замечание — единая схема (для JSON-отчёта)

| Поле | Значение |
|---|---|
| id | уникальный в рамках проверки (F-1, F-2… или UUID) |
| priority | Критично / Важно / Желательно / Вопрос |
| type | подтверждённая / вероятная / предположение / субъективная |
| location | O-имя материала + маркер привязки (страница / лист+строка / абзац / строка) |
| evidence | цитата из разрешённой копии (обрезана; секреты и контактные ПД замаскированы) |
| problem | что не так |
| consequence | что из этого следует |
| recommendation | как исправить |
| confidence | степень уверенности автора |

Правило классификации: доказательств недостаточно → тип не «подтверждённая», без исключений. «Подтверждённая» может опираться на: цитату (факт-аудитор, с маркером привязки до исходника), вычислимую проверку скрипта (числа/даты/схемы) — и ни на что больше.

## 8. Оценка и вердикт

- Шкала по критериям (адаптируется под тип документа): 0 — не выполнено, 1 — существенные недостатки, 2 — частично, 3 — хорошо, 4 — полностью и подтверждено; N/A; «Не проверено». Непроверенный критерий не даёт полной оценки без оговорки.
- Вердикт: **Принято / Принято с замечаниями / Не принято.** Критичная проблема или невыполнение обязательного требования блокирует «Принято». Итог не выводится из среднего балла.
- Гибрид: Медвежка принимает риск — в отчёте раздел «Принятые пользователем риски», техвердикт неизменен, событие в журнале.

## 9. Отчёты

Два файла на запуск, общий **run_id**: `<run_id>.md` (человекочитаемый) и `<run_id>.json` (структурированный). JSON-схема (поля): `run_id, created_utc, object{type, materials[] (O-имя, формат, объём)}, goal, preflight_summary{experts[], models[], depth}, findings[] (поля §7), verdict, scores{criterion → 0..4|N/A|«Не проверено»}, expert_disagreements[], checked_areas[], unchecked_areas[], limitations[], recommendations[], token_stats (пометка «оценка»), accepted_risks[], editor_stage{status, fixed[], unfixed[]}, retention_until, schema_version`.

Исходные пути и исходные имена материалов в отчёты не пишутся — только O-имена (§11).

При включённой редактуре к двум файлам отчёта добавляются два артефакта в тот же каталог `reports\<run_id>\`: `edited_O*.md` (маскированная исправленная копия) и `changes_O*.md` (пояснения: что исправлено, почему, основание — какое замечание, какие подтверждённые не удалось исправить и почему). В MD-отчёте достаточно указать, что редактура выполнена, и дать ссылки на оба результата. Правка в пояснениях указывается как: ID замечания → что изменено → статус (исправлено / не исправлено) → причина, если исправить не удалось. Так пользователь видит и сделанное, и нерешённое.

Разделы MD: общий вердикт → краткое обоснование → оценка по критериям → критичные → важные → желательные → вопросы → разногласия экспертов (судья сохраняет обоснованные, не глушит) → проверенные области → непроверенные области → ограничения → рекомендации и порядок исправлений → результаты редактуры: ссылки на `edited_O*.md` и `changes_O*.md` (при редактуре) → статистика токенов (пометка «оценка») → принятые пользователем риски → срок хранения.

## 10. Журнал JSONL

`D:\expert-panel\history\history.jsonl`, append-only. Идентификаторы:

- **run_id** — общий UUID запуска; повторяется во всех его событиях;
- **event_id** — уникальный идентификатор события;
- **seq** — **глобальная** сквозная нумерация по всему журналу.

Типы событий MVP: `run_started, preflight_shown, preflight_approved, finding_detected (O-имя, маркер, тип — без значения), phase_experts_started, expert_finished (роль, модель, оценка токенов), checkpoint_passed, judge_finished, report_saved (пути отчётов, retention_until), risk_accepted_by_user, retention_cleanup_proposed, report_deleted (run_id, когда), run_finished, run_stopped (причина), journal_repaired (repair_id, описание)`.

**ПД в журнале:** материалы — только O-имена; исходные пути и имена файлов в журнал и технические логи не пишутся (путь вида `D:\candidates\Иванов_Иван\resume.docx` сам содержит ПД).

**Надёжность:**

- Один активный запуск: инструкция + механизм — `run.lock` (PID + run_id); живой чужой lock → отказ; lock мёртвого процесса → снятие по подтверждению.
- Запись — одна полная строка за вызов, с `\n` и flush.
- Повторная запись того же `event_id` — отвергается с явной ошибкой (идемпотентность).
- **Восстановление после повреждения — с repair_id:** неполная последняя строка помечается `check` и не трогается молча. Процедура — только по подтверждению: (1) в `history.quarantine` (append-only) пишется заголовок переноса `{repair_id, utc_ts, seq, причина}` и сама повреждённая строка; (2) в журнал сразу записывается `journal_repaired` **с тем же repair_id**; (3) следующий `seq` = максимальный валидный `seq` + 1 (по журналу после переноса). Если запись `journal_repaired` не удалась — `check` видит незакрытый перенос (запись в quarantine без события с совпадающим repair_id) и повторяет **только запись события**, без повторного переноса. Несколько восстановлений различаются однозначно — по repair_id. Промежуточное состояние всегда видно `check`-ом, а не скрыто.
- **Целостность без хеш-цепочки** (отложена): `journal.py check` — каждая строка парсится как JSON, `seq` непрерывен глобально, `event_id` уникальны, каждый `run_id` имеет `run_started`, каждый перенос в quarantine закрыт событием с совпадающим repair_id.
- **Удаление:** Медвежка может удалить файлы отчёта; в журнал пишется `report_deleted`. Прежние события не переписываются никогда. Полная физическая очистка истории — не MVP.

## 11. Секреты и персональные данные

**Секреты:**

1. Сканирование — **по извлечённому тексту в памяти** (после `extract_text.py`), не по бинарному содержимому: регэкспы по сырым DOCX/XLSX/PDF не обнаруживают секреты надёжно. md/txt — сканирование текста; docx/xlsx — извлечённое из контейнеров; pdf — текстовый слой.
2. Нечитаемые, зашифрованные материалы и **PDF без извлекаемого текста** (скан-изображения, пустой результат извлечения) — статус **«не проверено на секреты»**, а не «проверено, находок нет». Честно отражается в Preflight и отчёте как ограничение. Нельзя заявлять проверку, которой не было. OCR — вне MVP.
3. Скрипт выводит только O-имя, маркер привязки, тип. Значения не попадают ни в stdout, ни в stderr, ни в диагностические логи — гарантия тестируется на этапе 0.
4. Порядок: сканер находит (текст в памяти) → Preflight показывает → Медвежка выбирает режим → скрипт формирует разрешённые копии (извлечение повторно в памяти → обработка → запись) → только после этого чтение координатором и экспертами. Копии не создаются до выбора режима.
5. **Промежуточный немаскированный текст не существует на диске:** только в памяти скриптов (шаги 3–7); временные открытые файлы запрещены; первый дисковый артефакт — маскированная разрешённая копия. Доступ к `D:\expert-panel\` — только у Медвежки (локальный диск, без сетевого доступа).
6. Значение секрета не попадает: в диалог, в брифы, в заключения, в отчёты, в журнал. Судья и `report.py` дополнительно прогоняют пост-маску по финальным текстам.

**Персональные данные (пилот — резюме):**

- **Контактные ПД — отдельная категория от секретов, отдельные паттерны** (телефоны РФ, email, адреса): обнаружение и маскирование в разрешённых копиях **во всех режимах без исключений** (режим из Preflight определяет только судьбу секретов) + пост-маска по заключениям экспертов и финальному отчёту (эксперт может воспроизвести контакт в замечании — маска обязана поймать). Тест — этап 0.
- ФИО, компании, должности, даты **не маскируются** — без них предметная экспертиза резюме невозможна (согласовано с Жорой).
- **ПД в путях:** исходные пути и имена материалов не попадают в журнал, логи и отчёты. Материалы обозначаются обезличенными O-именами с шага инвентаризации; если само имя файла содержит ПД (`Иванов_резюме.docx`) — используется только O-имя. Полные пути существуют лишь в ephemeral диалоге текущего запуска.
- В журнал ПД не попадают.
- Отчёты локальные, доступ — один человек (Медвежка).
- **Срок хранения:** `retention_days`, по умолчанию **90** (допущение; Медвежка может поменять). В каждом отчёте — `retention_until`. Авточистки нет: при каждом запуске координатор предлагает удалить просроченные — удаление только по подтверждению, событие `report_deleted`.

## 12. Recheck и сравнение

- Recheck = новый запуск, новый Preflight, новое разрешение. Координатор изучает исправленные участки, определяет связанные части, предлагает объём повтора.
- Сравнение с прошлым отчётом: **скрипт готовит кандидатов** (location + категория + пересечение ключевых слов), **классификацию делает координатор**. Метод помечается в отчёте сравнения.
- Категории: новые / устранённые / повторившиеся / изменившиеся. Сравнение не подменяет новый вердикт.

## 13. Скрипты Python (технические операции, решений не принимают)

| Скрипт | Что делает |
|---|---|
| `extract_text.py` | md/txt — как есть; docx — python-docx; xlsx — openpyxl; pdf — текстовый слой. Результат — только в память, промежуточные файлы на диск не пишет. Маркеры привязки (страница / лист+строка / абзац / строка). Статусы: «извлечено» / «не извлекается» (повреждён, зашифрован, скан без текстового слоя, пустой результат) — явные, не молча |
| `scan_secrets.py` | сканирует извлечённый текст **в памяти**: секреты + контактные ПД (два набора паттернов); вывод O-имя/маркер/тип без значений (stdout/stderr/логи чисты); после выбора режима формирует разрешённые копии в `work\<run_id>\` (извлечение повторно в памяти → маскирование секретов по режиму → контактные ПД всегда → запись) |
| `check_numbers.py` | вычислимое: числа, даты, суммы, схемы — внутренняя непротиворечивость документа |
| `journal.py` | append / list / read / check / lock (run.lock: создание, проверка PID, снятие); обнаружение остатков `work\` от незавершённых запусков; перенос повреждённого хвоста в quarantine с заголовком {repair_id…} + запись `journal_repaired` с тем же repair_id — по подтверждению |
| `report.py` | сборка MD+JSON из данных вердикта, валидация схемы, **пост-маска секретов и контактных ПД по всем финальным текстам**, retention_until; при редактуре — включает в отчёт статус редакторского этапа (`editor_stage`) и ссылки на `edited_O*.md`/`changes_O*.md` (новых скриптов не вводится) |
| `compare_reports.py` | подбирает кандидатов на сопоставление замечаний (location + категория + ключевые слова); классификация — за координатором |

Общее правило: ни один скрипт не пишет в проверяемые материалы, не удаляет данные без подтверждения, не создаёт немаскированных копий на диске и не принимает решений за пользователя.

## 15. Приёмка MVP

Комиссия готова к пилоту, когда за один полный прогон: lock получен → остатки проверены → материалы проинвентаризированы (O-имена) → текст извлечён в память (включая docx/xlsx/pdf, статусы явные) → секреты и контакты просканированы по извлечённому тексту → Preflight показан (находки + режим) → разрешение получено → разрешённые копии созданы (единственный дисковый артефакт) → эксперты отработали независимо → судья свёл → вердикт обоснован → MD+JSON созданы, пост-маска прошла → события в журнале, `journal.py check` проходит → work очищен, lock снят → исходные материалы не изменены (`git status`/сравнение хешей).

**Тесты этапа 0 (обязательные):** секрет в docx/xlsx/pdf обнаруживается (контейнерные форматы); PDF-скан без текстового слоя → «не проверено на секреты», а не «секретов нет»; значения отсутствуют в stdout/stderr/логах; контактные ПД замаскированы в копии, заключениях и отчёте (эксперт воспроизвёл email → пост-маска поймала); после Preflight (до утверждения) в `work\<run_id>\` нет ни одного файла; пустые значения → дефолты; lock (двойной запуск → отказ); остатки work (обнаружение → удаление по подтверждению); journal check (повреждённый хвост → quarantine с repair_id + journal_repaired с тем же repair_id, seq восстановлен); дубликат event_id → ошибка.

**Тесты редактуры (этап v1.4):** исходник и разрешённая копия не изменены после редактуры (хеши совпадают); итоговая редактура маскирована (контакты — масками, не реальные); корректор исправил только подтверждённые замечания (вероятные/предположения/субъективные не тронуты); добавление нового факта или незаявленного содержательного изменения ловится проверкой diff и результат не публикуется; создаются оба файла `edited_O*.md` и `changes_O*.md`; маски контактов сохранены после правки.

**Базовые критерии пилота (резюме, согласованный состав без изменений):** соответствие целевой позиции / фактическая достоверность / полнота обязательных блоков / структура и подача / **консистентность**.

**Пилот:** 3 реальных резюме от Кадровика. Успех = Медвежка признаёт замечания полезными (доказательные, без выдумок), а не формально пройденный чек-лист.
