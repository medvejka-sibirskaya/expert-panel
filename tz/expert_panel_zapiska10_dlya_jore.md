Главный факт: **ни один из трёх не проверяет документы нашей предметной области и не доказывает, что комиссия лучше одного сильного агента на наших типах документов.** Это согласуется с твоим выводом — выбор решает эксперимент на одинаковых материалах, не примеры. Дополнительно отметим: у всех трёх нет ничего похожего на наш ПД-контур (маскирование контактов, пост-маска отчётов) и механическую проверку цитат скриптом.

## 2. Переносимое (список для проработки, приоритет по номерам)

1. **Промпт критика для режима B** (adversarial-review): четыре типа оспаривания — «находка реальна или false positive?», «предложенный фикс не создаёт новых проблем?», «severity пропорциональна рискам?», «есть ли более простая безопасная альтернатива?» + самонапоминание «если соглашаешься со всем — перепроверь себя». Прямая заготовка для брифа критика в варианте B.
2. **Анти-консенсус в судью** (agent-review-panel): «полное согласие экспертов одной модели — один источник, а не независимая верификация»; консенсус без новых доказательств не повышает класс до «подтверждённой». У нас волна целиком на GLM — это дешёвый аналог меры против коррелированных ошибок.
3. **Severity dampening**: находка без конкретной цитаты/привязки не может быть выше «вероятной», сколько бы голосов ни собрала. Ложится на существующий `verify_evidence`.
4. **Post-judge gate**: проверка собственных находок судьи отдельной петлёй — у нас судья в единственности никем не проверяется (R3 показал цену этого слепого пятна).
5. **Экономика координатора** (agent-review-panel): их аудит — 69% токенов ест координаторский цикл против 7% у агентов. Приёмы: батчинг вызовов, «возврат субагента — путь + ≤50 слов, полный текст на диск».
6. **Границы автофикса** (adversarial-review): единый бар для редактуры — консенсус + высокая уверенность + критичность; после правки проверяются только внесённые регрессии, «pre-existing не автофиксится». Усиливает наши правила §5а.
7. **Таблица «утверждение vs доказательство vs минимальная формулировка»** (peer-review) и NULL-гипотеза («документ оверклеймит, пока не доказано») — в брифы фактов.

Честные оговорки: часть ярлыков agent-review-panel (conformity-метки, «калиброванный скептицизм 20–60%») дословно в файлах не нашлась — беру из пересказов README, при внедрении сверить с первоисточником. «60 секунд» PRD Reviewer не проверялись.

## 3. Дефект `verify_evidence.py` — подтверждён, принимается

Проверила по коду твоё замечание: да, `verify_finding()` сверяет только O-имя и текст цитаты — **маркер расположения игнорируется**. Замечание «O1, строки 7–9» с цитатой, фактически лежащей в строках 1–3, вернёт `verified`. В реальных findings прогона локация задаётся диапазоном строк («O1, строки 7–9, [Опыт]»), так что проверка локации — механически реализуема: цитата (каждый её фрагмент) должна найтись в заявленном диапазоне строк копии; цитата в файле, но вне диапазона → `mismatch` с указанием, где нашлось; диапазон не указан — прежняя поведение с пометкой.

План: исправление + отдельные тесты на `verify_evidence.py` (их действительно нет) и `check_numbers.py`. Срок — до пилота, независимо от исхода сравнения архитектур.

Оговорки по твоему ревью, не несогласие, а контекст: (а) два упавших теста на Linux — артефакт пакета: фикстуры сознательно не включались (описано в README пакета), а PID-тест журнала использует `cmd /c exit` — целевая среда Windows; (б) тезис «verified ≠ доказательство правильности замечания» разделяем: скрипт проверяет привязку доказательства, семантика остаётся за судьёй — это и зафиксировано в его докстринге.

## 4. Уточнение к плану сравнения режимов (твой ответ №9)

Предлагаю добавить **шаг 0: замер экономики координатора** до/параллельно с экспериментом — иначе сравнение A/B/C измерит не «комиссия vs один агент», а «текущие накладные координации vs агент». Ориентир — их аудит: накладные координатора могут доминировать над стоимостью самих агентов (69% против 7%). Приёмы переноса: батчинг, компактные возвраты субагентов с полным текстом на диск, подсчёт токенов по фазам (в отчётах уже есть token_stats, нужна детализация по этапам).

Анти-консенсус и severity dampening (п. 2–3 выше) — вносим в судьи независимо от исхода сравнения: они нужны в любом из трёх режимов.
