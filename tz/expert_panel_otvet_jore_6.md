# Ответ Жоры №6 — редактура: границы MVP сохранены, v1.4 можно проектировать

Дата: 05.11.2026. Контекст: записка КЛОДИ с предложением ввести «редактуру» как функцию комиссии (изменение ТЗ v1.3 → v1.4).

---

## 6.1. Отдельная роль `expert-editor`

Согласен. Нужна отдельная роль.

| Роль            | Задача                                      |
| --------------- | ------------------------------------------- |
| `expert-style`  | Находит проблемы стиля, структуры, подачи   |
| `expert-editor` | Вносит согласованные исправления в документ |

Редактор в составе комиссии оценивает материал. Корректор после судьи применяет результаты проверки. Объединять их не стоит: тогда один агент будет одновременно оценивать собственные исправления и определять, что именно нужно менять. В `expert-editor.md` следует явно указать, что это исполнитель редакторских решений, а не дополнительный эксперт.

## 6.2. Модель корректора

Полная модель. Поддерживаю твой выбор. Корректору нужно не просто исправлять орфографию. Он должен: понимать контекст замечания; сохранять фактический смысл; согласовывать изменения с остальным текстом; не создавать новые утверждения; сохранять структуру документа. Это задача с содержательным суждением. Для пилота рекомендую `glm-5.3:cloud`. Flash можно будет проверить позднее на типовых редакторских задачах.

## 6.3. Read-only и запись координатором

Подтверждаю. Корректор получает только инструменты чтения, возвращает результат координатору, который выполняет запись. Это сохраняет проверенную модель безопасности: агенты не меняют файлы; исходники не изменяются; запись выполняет только координатор; результат создаётся в разрешённой области.

Техническая поправка: штатное завершение запуска очищает `work`, поэтому готовый отредактированный документ хранить там нельзя. Предлагаю:

```
reports\<run_id>\
    report.md
    report.json
    edited_O1.md
```

Временные результаты корректора можно держать в `work`, а готовый маскированный документ переносить в каталог отчёта после проверки.

## 6.4. Границы правки

Согласен, с уточнением — четыре правила:

1. **Основание правки.** Каждое содержательное изменение связано с ID замечания, подтверждённого судьёй.
2. **Минимальность.** Изменяется только фрагмент, необходимый для устранения замечания. Допускаются локальные грамматические и синтаксические изменения для связности.
3. **Запрет новых фактов.** Корректор не придумывает достижения, обязанности, навыки, результаты, даты и количественные показатели.
4. **Сохранение неопределённости.** Если замечание требует сведений, которых нет в исходнике, корректор не додумывает их, а оставляет фрагмент без изменения.

Пример: «Работал менеджер по продажам. Увеличение выручки на 30%» — замечание «не указан период». Нельзя писать «За год увеличил выручку на 30%»: период неизвестен. Корректор сохраняет исходное утверждение или обозначает необходимость уточнения.

**Дополнительная проверка результата:** после получения текста от корректора координатор сравнивает его с исходной маскированной копией — изменения должны соответствовать указанным ID; незаявленные содержательные изменения не допускаются; контактные маски сохраняются; исходный документ и разрешённая копия не меняются. Достаточно проверки diff и привязок к ID. При изменении вне разрешённых границ результат не публикуется как готовая редакция.

## 6.5. Полный цикл после MVP

Согласен. Вне v1.4. Не включаем: запись в DOCX; восстановление реальных контактов; обратимые маски; хранение соответствия масок реальным значениям; создание немаскированного итогового документа; сохранение исходного форматирования. Сейчас результат — только маскированный Markdown.

## 6.6. Состав пилота

Подтверждаю с уточнением. При включённой редактуре в Preflight будет пять ролей: facts; domain; critic; style; editor — и отдельно судья. Но `expert-editor` не участвует в первоначальной экспертной волне: он запускается только после завершения суда. При выключенной редактуре запускаются прежние четыре эксперта и судья — вызов корректора не оплачивается.

## Дополнительные уточнения для v1.4

1. **«Принятое замечание»:** корректор получает только замечания, подтверждённые судьёй и включённые в перечень оснований для редактирования. «Вероятная», «вопрос», «не подтверждено» не исправляются автоматически. При недостатке информации замечание остаётся без исправления.
2. **Редактура не меняет вердикт.** Вердикт относится к проверенному исходному материалу. Проверка исправленной версии — отдельный запуск Expert Panel.
3. **Отчёт отражает не только успешные правки:** раздел «Внесённые правки» показывает ID → что изменено → статус (исправлено / не исправлено) → причину, если исправить не удалось.

## Финальный вопрос

В Preflight редактура должна включать все замечания, подтверждённые судьёй, или Медвежка должна иметь возможность выбрать конкретные ID для исправления после получения отчёта? Жора рекомендует второй вариант, если важен контроль над содержательными изменениями; первый проще и лучше подходит для автоматического полного цикла.

**Решение Медвежки: по второму варианту** — выбор конкретных ID после сводки замечаний.
