# ТЗ: Expert Panel («Экспертная комиссия») — реализация MVP v0.1

**Версия:** 1.1 от 04.11.2026 (заменяет v1.0)
**Статус:** концепция согласована с ревьюером (Жора, 04.11: «разбор корректный, все 6 замечаний закрыты»); финальная сверка и сверка §16 по документации Claude Code — до кода
**Источники:** спецификация MVP v0.1 (чаты с ChatGPT, файл 5), записка для Жоры от 04.11, ревью ТЗ v1.0 (Жора) + согласование правок, аудит hiring-panel (Maxikozie)

## 1. Что строим

Скилл Claude Code **`/expert-panel`** — независимая экспертная комиссия: проверка документов, сборка доказательных замечаний, вердикт, отчёт, журнал запусков.

- **Объекты MVP:** промпты, ТЗ, КП, резюме. **Первый пилот — резюме** (связка с Кадровиком: он готовит → комиссия проверяет → замечания возвращаются ему).
- **Вне MVP:** код, проекты, скиллы, n8n-workflows; SQLite, хеш-цепочки, внешние уведомления, PDF/HTML-экспорт, автоматические исправления, мониторинг (§15 спеки — без изменений).
- **Форматы чтения** (что система технически умеет читать): md, txt, docx, pdf, xlsx. Код и ipynb в MVP исключены полностью.
- **Разделитель ролей:** Библиотекарь (существующий скилл `librarian`, маршрутизация) ≠ Комиссия (`/expert-panel`, глубокое ревью). Комиссия ничего не знает про Библиотекаря и наоборот; связка — отдельная будущая задача.

## 2. Принципы (перечислены в SKILL.md как ограничения поведения)

1. Независимость экспертов: свежий контекст каждому, параллельная волна, заключения друг друга не видят.
2. Каждое замечание — с доказательством (цитатой); без доказательства — не факт, а предположение с пометкой.
3. Скрипты проверяют только форматы и вычислимое (числа, даты, схемы); свободные утверждения сверяет только эксперт-аудитор фактов по цитатам из исходника — скриптовая проверка чисел семантические выдумки не ловит.
4. Комиссия ничего не изменяет в проверяемом материале, не запускает код, не ходит в сеть.
5. Запуск — только после явного разрешения; Preflight ≠ разрешение.
6. Оценки токенов — диапазоном с пометкой «оценка», без денег; оценочное не выдаётся за фактическое.
7. Язык отчётов — русский; имена файлов, технологий, переменных — в оригинале.
8. Гибридный вердикт: комиссия даёт техвердикт; Медвежка может отдельно принять риск — вердикт это не меняет, факт фиксируется в журнале и отчёте.
9. Один активный запуск в момент времени — обеспечивается не только инструкцией, но и механизмом lock-файла (§10).
10. Значения потенциальных секретов не выводятся сканером ни в stdout, ни в stderr, ни в диагностические логи (§11).

Префикс `expert-` — чтобы не пересекаться с агентами Медвежки (`barrymore`, `kadrovik`…) и чтобы файлы комиссии стояли в списке одним блоком. Имена файлов агентов — латиница в нижнем регистре (требование Claude Code); названия ролей и весь текст внутри — русские.

Определения агентов дают две гарантии: набор инструментов `Read, Glob, Grep` (редактировать нечем) и закреплённую модель за ролью.

## 4. Роли и модели

Точные идентификаторы (подтверждены Медвежкой 04.11): **полная** = `glm-5.3:cloud`, **флэш** = `glm-5.3-flash:cloud`. Модель — параметр frontmatter роли: замена модели (в т.ч. будущие DeepSeek/Kimi) архитектуру не меняет.

| Роль | Модель по умолчанию | Что делает |
|---|---|---|
| expert-facts (аудитор фактов) | полная | сверяет утверждения документа с исходником по цитатам; ловит выдумки |
| expert-domain (предметник) | полная | экспертиза по типу документа (для пилота — HR/резюме) |
| expert-critic (критик) | флэш | adversarial-взгляд: слабые места, пробелы, риски |
| expert-style (редактор) | флэш | типовые проверки: структура, ясность, формат, консистентность |
| expert-judge (судья) | **только полная** | сводит, проверяет доказательства, вердикт |

Численность (ориентиры, уточняются практикой): простая проверка — 2–3 эксперта, стандартная — 3–4, глубокая — 5–7. Координатор может поменять модель конкретному эксперту с обоснованием в Preflight — согласуется отдельной строкой. Смешение моделей внутри одного прогона — только по явному решению Медвежки в Preflight.

**Состав пилота (резюме, стандартная глубина):** expert-facts + expert-domain (HR) + expert-critic + expert-style — 4 эксперта, судья expert-judge. Редактор исключается при целевой проверке фактов — по решению в Preflight.

## 5. Сценарий запуска (ядро SKILL.md)

0. **Блокировка:** `journal.py lock` создаёт `run.lock` (PID + run_id). Живой чужой lock → запуск отказан (параллельные комиссии запрещены); lock от мёртвого процесса → снятие по подтверждению Медвежки. Снятие lock — в конце запуска, включая остановку.
1. **Вход:** `/expert-panel` + материалы (файлы/пути; по умолчанию — из диалога или от Кадровика). КЛОДИ-главная принимает роль координатора.
2. **Инвентаризация без чтения содержимого:** Glob + метаданные (имя, размер, формат). Read на этом шаге не выполняется. Лимиты: файл ≤ 5 МБ, ≤ 20 файлов на запуск; сверх — согласование в Preflight (допущение, Медвежка может поменять).
3. **Секреты — до всякого чтения агентами:** `scan_secrets.py` по сырым файлам. Скрипт читает сам и выводит только файл/строка/тип — значения не попадают ни в диалог, ни в stdout/stderr, ни в логи. Сразу создаёт маскированные копии → `work\<run_id>\`.
4. **Чтение координатором — только разрешённых копий** (в маскированном режиме): тип объекта, объём, границы; нерелевантное исключает и показывает в Preflight.
5. **Preflight** (раздел 6) → показывается в чате.
6. **Явное разрешение.** Молчание/«посмотрим» ≠ разрешение.
7. **Волна экспертов:** все субагенты запускаются **одним сообщением** (параллельно, свежий контекст каждому). Бриф эксперта = роль + **пути разрешённых копий** + формат замечаний. Про чужие заключения в брифе ни слова.
8. **Стык-контроль:** координатор сравнивает фактический расход (оценка по объёму брифов/ответов) с согласованным Preflight. В пределах — дальше; превышение резерва — стоп и вопрос Медвежке. Механической остановки внутри фазы нет — контроль только на стыках.
9. **Судья:** expert-judge получает все заключения + **те же разрешённые копии** (может перечитать сам), объединяет дубли, проверяет доказательства, классифицирует, выносит вердикт.
10. **Отчёт + журнал:** `report.py` рендерит MD и JSON с общим run_id; `journal.py` дописывает события. Координатор проверяет просроченные отчёты (retention, §11) и предлагает их удалить — только по подтверждению.
11. **Очистка:** `work\<run_id>\` удаляется (копии сохраняются только по явной просьбе Медвежки), lock снимается, резюме показывается в чате.

## 6. Preflight — обязательный состав

1. Цель проверки и тип задачи
2. Изученные материалы (пути + объём) и исключённое (кэш, нерелевантное, нечитаемое); отклонения от лимитов — с обоснованием
3. Глубина: целевая / связанная / комплексная — и границы проверки
4. Состав экспертов, роли, модели (включая отклонения от профиля — с обоснованием)
5. Предполагаемое количество вызовов (эксперты + судья + резерв)
6. **Оценка токенов диапазоном** (input/output раздельно, пометка «оценка», без денег)
7. Ограничения и неопределённости (что проверить не сможем)
8. Критерии приёмки (для пилота — базовый набор §15)
9. Место сохранения отчётов (по умолчанию `D:\expert-panel\reports\`; в папку проверяемого проекта — только в отдельную подпапку, утверждённую здесь же) **и срок хранения** (retention_days, §11)
10. Режим конфиденциальности + находки `scan_secrets` (файл/строка/тип, без значений) и предлагаемый способ обработки
11. Предложение сравнения с предыдущей проверкой (если объект уже проверялся)

**После утверждения Preflight** координатор не может сам: добавить экспертов, сменить модели, добавить этапы, расширить резерв вызовов. Любое изменение — новое согласование. Recheck — всегда новый запуск с новым Preflight.

## 7. Замечание — единая схема (для JSON-отчёта)

| Поле | Значение |
|---|---|
| id | уникальный в рамках проверки (F-1, F-2… или UUID) |
| priority | Критично / Важно / Желательно / Вопрос |
| type | подтверждённая / вероятная / предположение / субъективная |
| location | файл, строка или раздел документа |
| evidence | цитата из исходника (обрезана; контактные данные и секреты замаскированы) |
| problem | что не так |
| consequence | что из этого следует |
| recommendation | как исправить |
| confidence | степень уверенности автора |

Правило классификации: доказательств недостаточно → тип не «подтверждённая», без исключений. «Подтверждённая» может опираться на: цитату исходника (факт-аудитор), вычислимую проверку скрипта (числа/даты/схемы) — и ни на что больше.

## 8. Оценка и вердикт

- Шкала по критериям (адаптируется под тип документа): 0 — не выполнено, 1 — существенные недостатки, 2 — частично, 3 — хорошо, 4 — полностью и подтверждено; N/A; «Не проверено». Непроверенный критерий не даёт полной оценки без оговорки.
- Вердикт: **Принято / Принято с замечаниями / Не принято.** Критичная проблема или невыполнение обязательного требования блокирует «Принято». Итог не выводится из среднего балла.
- Гибрид: Медвежка принимает риск — в отчёте раздел «Принятые пользователем риски», техвердикт неизменен, событие в журнале.

## 9. Отчёты

Два файла на запуск, общий **run_id**: `<run_id>.md` (человекочитаемый) и `<run_id>.json` (структурированный). JSON-схема (поля): `run_id, created_utc, object{type, sources[]}, goal, preflight_summary{experts[], models[], depth}, findings[] (поля §7), verdict, scores{criterion → 0..4|N/A|«Не проверено»}, expert_disagreements[], checked_areas[], unchecked_areas[], limitations[], recommendations[], token_stats (пометка «оценка»), accepted_risks[], retention_until, schema_version`.

Разделы MD: общий вердикт → краткое обоснование → оценка по критериям → критичные → важные → желательные → вопросы → разногласия экспертов (судья сохраняет обоснованные, не глушит) → проверенные области → непроверенные области → ограничения → рекомендации и порядок исправлений → статистика токенов (пометка «оценка») → принятые пользователем риски → срок хранения.

## 10. Журнал JSONL

`D:\expert-panel\history\history.jsonl`, append-only. Идентификаторы разделены (правка по ревью Жоры):

- **run_id** — общий UUID запуска; повторяется во всех его событиях;
- **event_id** — уникальный идентификатор события;
- **seq** — **глобальная** сквозная нумерация по всему журналу (непрерывность проверяется глобально).

Типы событий MVP: `run_started, preflight_shown, preflight_approved, secret_finding (только файл/строка/тип, без значения), phase_experts_started, expert_finished (роль, модель, оценка токенов), checkpoint_passed, judge_finished, report_saved (пути, retention_until), risk_accepted_by_user, retention_cleanup_proposed, report_deleted (run_id, когда; содержимое отчёта не попадает), run_finished, run_stopped (причина), journal_repaired (описание переноса в quarantine)`.

**Надёжность (по ревью Жоры):**

- Один активный запуск: инструкция + механизм — `run.lock` (PID + run_id); живой чужой lock → отказ; lock мёртвого процесса → снятие по подтверждению.
- Запись — одна полная строка за вызов, с `\n` и flush.
- Неполная последняя строка: `journal.py check` помечает и **не трогает молча**; перенос в `history.quarantine` + событие `journal_repaired` — только по подтверждению Медвежки.
- Повторная запись того же `event_id` — отвергается с явной ошибкой (идемпотентность).
- **Целостность без хеш-цепочки** (отложена, решение Медвежки 04.11): `journal.py check` — каждая строка парсится как JSON, `seq` непрерывен глобально, `event_id` уникальны, каждый `run_id` имеет `run_started`.
- **Удаление (согласованная политика):** Медвежка может удалить файлы отчёта; в журнал пишется `report_deleted`. Прежние события журнала не переписываются никогда. Полная физическая очистка истории — не MVP.

## 11. Секреты и персональные данные

**Секреты:**

1. `scan_secrets.py` (регэкспы: Bearer/token=/api_key=/password=, Telegram-токен, вебхуки) гоняется **до всякого чтения агентами** — эвристика, гарантии покрытия нет, честно отражается в Preflight и отчёте.
2. Скрипт выводит только «файл, строка, тип». Значения не попадают ни в stdout, ни в stderr, ни в диагностические логи — гарантия тестируется на этапе 0.
3. Варианты продолжения (выбирает Медвежка в Preflight): **(а)** маскированные копии — все работают только с ними (по умолчанию), **(б)** участок исключается из проверки, фиксируется как непроверенный, **(в)** остановка запуска.
4. Значение секрета не попадает: в диалог, в брифы экспертов, в заключения, в отчёты, в журнал. Судья и `report.py` дополнительно прогоняют маску регэкспов по финальным текстам.

**Персональные данные (пилот — резюме, по ревью Жоры):**

- Контактные данные (телефон, email, адрес) маскируются в цитатах и отчётах.
- ФИО, компании, должности, даты **не маскируются** — без них предметная экспертиза резюме невозможна (решение согласовано с Жорой).
- В журнал ПД не попадают (только run_id, пути, типы).
- Отчёты локальные, доступ — один человек (Медвежка).
- **Срок хранения:** параметр `retention_days`, по умолчанию **90** (допущение; Медвежка может поменять). В каждом отчёте — `retention_until`. Авточистки в MVP нет: при каждом запуске координатор проверяет просроченные отчёты и предлагает удалить — удаление только по подтверждению, событие `report_deleted`.

## 12. Recheck и сравнение

- Recheck = новый запуск, новый Preflight, новое разрешение. Координатор изучает исправленные участки, определяет связанные части, предлагает объём повтора.
- Сравнение с прошлым отчётом: **скрипт готовит кандидатов** (location + категория + пересечение ключевых слов), **классификацию делает координатор** (семантическая задача — по правилу «скрипты не принимают решений»). Метод помечается в отчёте сравнения.
- Категории: новые / устранённые / повторившиеся / изменившиеся. Сравнение не подменяет новый вердикт.

## 13. Скрипты Python (технические операции, решений не принимают)

| Скрипт | Что делает |
|---|---|
| `extract_text.py` | md/txt — как есть; docx/xlsx — python-docx/openpyxl; pdf — нативно Read. Форматы MVP: md, txt, docx, pdf, xlsx (код и ipynb исключены). Нечитаемое — отчёт «не читается», не молча |
| `scan_secrets.py` | эвристический поиск секретов по сырым файлам ДО чтения агентами; вывод файл/строка/тип; создаёт маскированные копии; значения не выводит нигде (stdout/stderr/логи) |
| `check_numbers.py` | вычислимое: числа, даты, суммы, схемы — внутренняя непротиворечивость документа |
| `journal.py` | append / list / read / check / **lock** (run.lock: создание, проверка PID, снятие) событий JSONL; перенос повреждённого хвоста в quarantine — по подтверждению |
| `report.py` | сборка MD+JSON из данных вердикта, валидация схемы, маска регэкспов по финальным текстам, retention_until |
| `compare_reports.py` | подбирает кандидатов на сопоставление замечаний (location + категория + ключевые слова); классификация — за координатором |

Общее правило: ни один скрипт не пишет в проверяемые материалы, не удаляет данные без подтверждения и не принимает решений за пользователя.

## 15. Приёмка MVP

Комиссия готова к пилоту, когда за один полный прогон: lock получен → материалы проинвентаризированы → секреты просканированы до чтения → маскированные копии созданы → Preflight показан → разрешение получено → эксперты отработали независимо (по разрешённым копиям) → судья свёл → вердикт обоснован → MD+JSON созданы и валидны → события в журнале, `journal.py check` проходит → work-копии очищены, lock снят → исходные материалы не изменены (`git status`/сравнение хешей).

**Тесты этапа 0 (обязательные):** маскирование секретов сканером (значения отсутствуют в stdout/stderr/логах), пустые значения → дефолты, lock (двойной запуск → отказ), journal check (повреждённый хвост → quarantine по подтверждению), дубликат event_id → ошибка.

**Базовые критерии пилота (резюме):** соответствие целевой позиции / фактическая достоверность / полнота обязательных блоков / структура и подача / формат и консистентность. Веса предметник предлагает в Preflight.

**Пилот:** 3 реальных резюме от Кадровика. Успех = Медвежка признаёт замечания полезными (доказательные, без выдумок), а не формально пройденный чек-лист.
