=== 2. РЕАЛИЗАЦИЯ ПО СКРИПТАМ (кратко, против ТЗ §13) ===

extract_text.py — md/txt/docx/xlsx/pdf в память, на диск не пишет. Маркеры
привязки: [страница N] (pdf), [лист «X», строка N] (xlsx), [абзац N] (docx),
«строка N» (md/txt). Статусы явные: «извлечено» / «не извлекается» (повреждён,
зашифрован, пустой файл, пустой результат — включая pdf-скан без текстового
слоя). CLI выводит только статус JSON, текст — никогда.

scan_secrets.py — два набора паттернов: секреты (Bearer, token=, api_key=,
password=/пароль=, Telegram-токен, вебхуки) и контактные ПД (email, телефоны
РФ, адреса «ул./просп./пер./шоссе … д. N»). scan работает по извлеченному
тексту в памяти, выводит только O-имя/маркер/вид/категорию — значения не
попадают ни в stdout, ни в stderr. prepare формирует разрешённую копию
(первый дисковый артефакт): секреты по режиму mask/exclude (строка с секретом
заменяется на «[УЧАСТОК ИСКЛЮЧЁН — не проверялся]»), контактные ПД — всегда
в любом режиме.

journal.py — append-only JSONL: seq глобальный (макс. валидный + 1), event_id
уникален (дубль — exit 3, явная ошибка), запись одной полной строкой с \n и
flush. run.lock (PID + run_id): живой чужой → отказ (exit 2); мёртвый → снятие
только с --confirm-stale. check: JSON-строки, непрерывность seq, уникальность
event_id, run_started у каждого run_id (кроме journal_repaired), закрытость
переносов. repair — только с --confirm: заголовок {repair_id, utc_ts, seq,
причина} + повреждённые строки в history.quarantine (JSONL), затем событие
journal_repaired С ТЕМ ЖЕ repair_id; незакрытый перенос (запись в quarantine
без события) дозакрывается ТОЛЬКО записью события, quarantine не растёт.
remains — остатки work\ от незавершённых запусков: обнаружение всегда,
удаление только с --confirm-delete. Для изоляции тестов: --root ДО подкоманды
(env EXPERT_PANEL_ROOT), боевой D:\expert-panel в тестах не используется.

report.py — MD + JSON с общим run_id, схема §9 (валидация обязательных полей
+ поля замечаний §7). ПОСТ-МАСКА секретов и контактных ПД по всем строкам
финальных данных (эксперт воспроизвёл контакт в замечании — маска ловит).
retention_until из retention_days; env EXPERT_PANEL_RETENTION_DAYS, ПУСТОЕ
значение = дефолт 90 (поведение env_ignore_empty).

check_numbers.py — вычислимое: валидность дат (включая 31.02 и високосные),
порядок «с X по Y», суммы вида «a + b = c» (с разрядными пробелами и дробями),
нумерация списков (дубли, пропуски). Семантика — экспертам, скрипт решений
не принимает. Не входит в 13 тестов §15, покрыт smoke-прогоном.

compare_reports.py — кандидаты на сопоставление замечаний двух отчётов:
location_match + категория (same_priority/same_type) + пересечение ключевых
слов (Жаккар по problem+recommendation, порог 0.2). Классификация — за
координатором. Не входит в 13 тестов, покрыт smoke-прогоном.

Пруфы по ключевым кейсам:
- секрет в docx/xlsx/pdf обнаруживается по извлечённому тексту (тест 1,
  включая фикстуру PDF с текстовым слоем — собрана руками, без OCR);
- pdf-скан без текстового слоя → «не проверено на секреты», НЕ «находок
  нет» (тест 2);
- значения секретов/ПД не встречаются ни в stdout, ни в stderr сканера
  (тест 3: Bearer, token, email, телефон, адрес);
- контактные ПД замаскированы в копии в обоих режимах (тест 4);
- пост-маска: email в evidence и password в problem замечания пойманы в обоих
  файлах отчёта (тест 5);
- до prepare в work\ нет ни одного файла, после — ровно один (тест 6);
- пустой EXPERT_PANEL_RETENTION_DAYS → retention_until = сегодня + 90 (тест 7);
- двойной lock → отказ; lock мёртвого PID → снятие только по подтверждению
  (тесты 8–9); нюанс Windows: PID переиспользуется мгновенно, тест берёт
  гарантированно мёртвый PID с проверкой OpenProcess и ретраями;
- остатки work\ → found без удаления, удаление только по --confirm-delete
  (тест 10);
- повреждённый хвост → check красный → repair --confirm → quarantine с
  repair_id + journal_repaired с тем же repair_id, seq восстановлен
  (макс. валидный 3, следующее событие — seq 4) (тест 11);
- незакрытый перенос → повтор ТОЛЬКО записи события, quarantine не растёт
  (тест 12);
- дубль event_id → exit 3, в журнале остаётся одно событие (тест 13).

=== 4. ВОПРОСЫ И РЕШЕНИЯ ДЛЯ ТВОЕГО РЕВЬЮ ===

4.1. PID в run.lock — чей процесс считать владельцем запуска? journal.py
короткоживущий: он создаёт lock и сразу завершается, его PID мёртв уже через
секунду. Сделан параметр --pid (по умолчанию — сам вызвавший процесс), т.е.
координатор обязан передавать PID долгоживущего владельца (сессии Claude
Code). Вопрос: как координатору его узнать в живом запуске — или признать
lock эвристикой (живой PID = «похоже, запуск идёт»), с чем согласуется §13
ТЗ («проверка PID»)?

4.2. repair переносит ВСЕ повреждённые строки журнала, не только хвостовой
блок. Для MVP повреждение хвоста — основной случай; середину молча не
обрезаем, перенос идентичен. Ок ли, или требовать ручного разбора для
серединных повреждений?

4.3. quarantine — JSONL (заголовок + строки как отдельные JSON-записи),
а не «заголовок + сырой текст». Так check парсит его тем же кодом. Ок?

4.4. check_numbers: набор проверок MVP (даты, их порядок, «a + b = c»,
нумерация). Осознанно НЕ сделали: извлечение табличных сумм из docx/xlsx
(нужна семантика структуры), проверку денежных форматов (« руб.», тыс./млн).
Дополнить или оставить экспертам?

4.5. compare_reports: Жаккар по problem+recommendation, evidence в токенах
не участвует (цитаты маскированные, могли бы шумить). Порог кандидата:
location ИЛИ категория ИЛИ overlap ≥ 0.2. Ок?
